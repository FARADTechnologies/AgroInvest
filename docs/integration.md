# EKTIS integration concept

The portal is designed to be integrated into the Ministry of Agriculture's Electronic
Agriculture Information System (EKTIS). The prototype never contacts the real EKTIS: it talks
to a test double (`ektis-mock/`, Java 21 + Spring Boot) that implements the same REST contract.

## What is exchanged

| Direction | Operation | When | Contract |
|---|---|---|---|
| Portal → EKTIS | Farmer registry lookup by FİN or VÖEN | the applicant checks their own identifier (wizard step 1, profile) | `GET /ektis/v1/farmers?fin=…` or `?voen=…` → farmer id, registration date, declared land, activities; 404 if not registered |
| Portal → EKTIS | Land-use decision | a specialist decides **Qalib** (or announces a plot result) | `POST /ektis/v1/land-use-decisions` → `EKTIS-LUD-YYYY-NNNNNN` reference |
| EKTIS → Portal | Decision registered (callback) | planned, phase 2 | `POST /api/v1/integration/ektis/events` with an HMAC signature |
| EKTIS → Portal | Parcel import | planned, phase 3 | parcels registered in EKTIS become farm areas |

The contract is published as OpenAPI: [`ektis-v1.openapi.yaml`](ektis-v1.openapi.yaml) (also
served by the mock at `/ektis/v1/api-docs` and `/swagger-ui.html`). Only winning decisions are
sent: EKTIS records who uses which land; a declined application changes nothing there.

## How a decision reaches EKTIS

```mermaid
sequenceDiagram
    participant S as Specialist
    participant API as Portal API
    participant DB as PostgreSQL
    participant W as Outbox worker
    participant E as EKTIS
    S->>API: Decide "Qalib" (reason)
    API->>DB: one transaction: application DECIDED + history + notification + outbox message
    API-->>S: 200 (the specialist never waits for EKTIS)
    loop every 3 s
        W->>DB: due messages (FOR UPDATE SKIP LOCKED)
        W->>E: POST land-use-decisions (X-API-Key, X-Request-ID, Idempotency-Key)
        alt 2xx
            W->>DB: SENT + EKTIS reference, log entry
        else error or unreachable
            W->>DB: attempt n failed, next attempt after 5, 10, 20, then 30 s; log entry
        end
    end
```

* **Transactional outbox** (`integration_outbox`): the decision and its message are committed
  together, so a decision can never exist without its message, and an EKTIS outage never blocks
  or loses a decision.
* **Retries** with growing delays; after 12 failed attempts a message is `FAILED` and a
  specialist can resend it from the "İnteqrasiya logu" screen. When an outage ends (the mock's
  fault switched off), waiting messages are delivered at once.
* **Idempotency**: the portal's decision id is the idempotency key (`decisionId` and the
  `Idempotency-Key` header). EKTIS answers a repeated decision with the original receipt (200
  instead of 201), so a retry after a timeout never registers twice.
* **Traceability**: every call carries `X-Request-ID`, which EKTIS echoes and logs. The portal's
  `integration_log` stores operation, HTTP status, duration, the id and a summary in which FİN and
  VÖEN are masked. Staff see it on `/admin/integration`, live.
* **Safe in several replicas**: delivery locks rows with `FOR UPDATE SKIP LOCKED`.

## Security of the exchange

* The portal authenticates with an API key (`X-API-Key`), compared in constant time by EKTIS.
  Keys live only in environment variables (`.env`, generated by `scripts/start.*`).
* The applicant can look up only their own identifier; the registry cannot be searched for other
  people through the portal.
* In production the exchange runs through the Electronic Government Information System (EHİS)
  with the authority's consent, typically over mutual TLS; phase 2 adds an HMAC-SHA256 signature on
  callbacks (`EKTIS_HMAC_SECRET` is already provisioned).

## Switching to the real system

The portal depends on a protocol, not on the mock (`api/app/modules/integration/client.py`):

```python
class EktisClient(Protocol):
    async def lookup_farmer(self, *, fin, voen, request_id) -> EktisResult: ...
    async def send_decision(self, payload, request_id) -> EktisResult: ...
```

`EKTIS_MODE=mock` selects `HttpEktisClient` against `EKTIS_BASE_URL`; `EKTIS_MODE=disabled` makes
no calls (messages wait in the outbox). A production client implements the same protocol against
the EHİS endpoint; nothing else in the portal changes. The steps:

1. Agree the contract with the EKTIS owner (start from `ektis-v1.openapi.yaml`).
2. Obtain access through EHİS and credentials (certificate or key) from the authority.
3. Implement the client for the agreed transport, set `EKTIS_MODE`, `EKTIS_BASE_URL` and the key.
4. Run the integration tests against the authority's test environment; switch over.

## Demonstrating it

1. Open **İdarəetmə paneli → İnteqrasiya logu** as `mutexessis@agro-demo.test`.
2. Press **Nasazlığı simulyasiya et** (the mock answers 503).
3. Decide **Qalib** on a reviewed application: the message stays **Növbədə**, failed attempts
   appear in the log.
4. Press **EKTİS-i bərpa et**: the message becomes **Çatdırılıb** with its EKTIS reference.
